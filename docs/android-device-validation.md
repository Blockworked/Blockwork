# Android fixture and device checks

The standalone `android-fixture` app supplies predictable targets for testing
Blockwork on Android 11–16. The instrumentation suite is built separately from
the production app and drives real Rust workflows through JNI and the bound
accessibility service. It does not add an exported test interface to Blockwork.

**Status:** the fixture, both main APKs and both instrumentation APKs build and
pass signature/alignment checks. The eleven device tests have **not run** in
this workspace: `adb devices` reports no connected devices. Existing software
emulator failures are recorded in [android-validation.md](android-validation.md).
Building the test APKs does not demonstrate successful Android automation.

## Build

Use the pinned SDK/Qt/NDK/JDK setup from [android.md](android.md), then run:

```sh
scripts/build-android.sh x86_64
scripts/build-android-validation.sh x86_64
# For an ARM64 device instead:
scripts/build-android.sh arm64-v8a
scripts/build-android-validation.sh arm64-v8a
```

The validation builder reuses Gradle 8.14.3 from the staged Qt package and checks
that the staged host/test Kotlin and Gradle configuration match current source.
It produces:

- `dist/android/blockwork-fixture-debug.apk` (no native ABI dependency)
- `dist/android/blockwork-x86_64-androidTest.apk`
- `dist/android/blockwork-arm64-v8a-androidTest.apk`

Install the instrumentation APK matching the main app's ABI. CI builds and
uploads these APKs with each ABI's main APK; it does not run connected tests.

## Run on a device

Use a dedicated, unlocked test device with empty Blockwork storage. The suite
refuses to create workflows if an unrelated workflow is running or stored macros
are not named `[fixture] ...`. It never clears app storage. Workflow permission
prompts generated by these tests are answered with Allow once.

Choose the device explicitly:

```sh
adb devices
python3 scripts/test-android-device.py --serial SERIAL --install-only
```

Open Blockwork and enable **Blockwork automation** in Accessibility settings.
For a sideloaded APK, the device may also need App info → menu → Allow restricted
settings. Unlock the device and leave it interactive, then run:

```sh
python3 scripts/test-android-device.py --serial SERIAL --skip-install
```

The runner selects a supported ABI from that device, installs APKs unless
`--skip-install` is given, and saves `device.json` and `instrumentation.txt` under
`target/android/device-validation/SERIAL/TIMESTAMP/`. Metadata records the SDK,
build fingerprint, page size and test options. A zero adb exit code alone is
not considered success: the runner checks the JUnit result and failure statuses.
`--class package.Class#method` can isolate a failure. For example:

```sh
python3 scripts/test-android-device.py --serial SERIAL --skip-install \
  --class 'com.blockworked.blockwork.FixtureDeviceTest#replacementAndFocusedInsertionHaveDifferentSemantics'
```

The optional revocation case temporarily removes Blockwork from enabled
accessibility services and restores the original list:

```sh
python3 scripts/test-android-device.py --serial SERIAL --skip-install --include-revocation
```

That case is skipped without the explicit option. Both the device test and host
runner restore the setting in `finally` blocks. The original value is also saved
in `device.json` when this option is used, so it can be restored manually if the
device disconnects or its process dies during the check. No accessibility grant
is automatically enabled during a normal install/run.

## Targets

All resource selectors use package `com.blockworked.fixture` and full resource
IDs such as `com.blockworked.fixture:id/input`.

| Scene | Stable targets and behavior |
| --- | --- |
| Main | `click_target`, `long_target`, `input`, `focus_middle`, duplicate `duplicate_target` buttons, `changing_target`, `replace_target`, `show_delayed`, `delayed_label` |
| Gesture | `gesture_area`: red/green/blue/yellow quadrants, tap/hold/swipe counters in `status` |
| Scroll | `scroll_panel`: long content; fixed `status` reports actual scroll offset |
| Password | `password`: a real password EditText, rejected for exposed-text insertion and reading |
| Secure | `FLAG_SECURE` window with the same visible four-color target |

The fixture launcher opens Main. Its buttons open the other scenes. For manual
checks, a scene can also be selected explicitly:

```sh
adb -s SERIAL shell am start -W -n com.blockworked.fixture/.MainActivity --es scene gesture
```

Duplicate buttons deliberately share both text and resource ID. Add content
description `duplicate 1` or `duplicate 2` to disambiguate. Replacing the changing
button destroys its old view and creates a new one with the same resource ID,
so stale-node assumptions can be exposed. Select beta focuses the text field
with only `beta` selected in `alpha beta`, making insertion observably different
from replacement. The fixture has no network/storage permissions or automation
service of its own.

## Coverage and remaining work

The eleven instrumented cases cover package launch through Home/launcher,
conjunctive/ambiguous selectors, fresh and delayed nodes, focused insertion vs
replacement, password rejection, physical-coordinate gestures, concurrent
strands, scrolling, catchable waits, stop, coalesced screenshots and exact color
samples, secure capture errors, and optional service revocation/reconnection.
Each test removes only the workflow it created.

The secure-capture test is deliberately strict: a masked black bitmap is a
failure, as is an unrelated capture error. The current display-screenshot
implementation may return a bitmap when Android masks secure layers. That
known requirement remains unresolved; do not skip or weaken this check to call
the release gate passed.

Six host-side checks exercise the CLI using a fake adb executable: they verify
success evidence, adb/JUnit failure handling, setting restoration, explicit
device selection, class-filter quoting, and install-only behavior. They do not
exercise Android. Run them with:

```sh
python3 -m unittest discover -s scripts/tests -p test_android_device_runner.py -v
```

Real device results on Android 11 and 16, physical ARM64 16 KB-page execution,
picker overlay exclusion/rotation, custom blocks, service/lock lifecycle,
editor Back/IME behavior, alarms under Doze/reboot/time changes, and a complete
workflow built on the phone are still required. Reliable long background jobs,
the remaining touch-target audit, reference display persistence, secure-layer
handling and upstream Blockstitch publication remain tracked in android.md.
